# 工程原则 (Engineering Principles)
> **本文件落实**: RULE-015（ruthlessly YAGNI）
> **另承载 RULE-057 §2「纵向小闭环」的正文**——RULE-057 的编号落点仍是 `rules/dev-learning-loop.md`，本节只是内容归并处，**不另行声明该编号**（一主题一份真源）。

> 本文件为 `AGENTS.md` 中 **RULE-015（ruthlessly YAGNI）** 的落点文件，与 `rules/collaboration.md` 的「最小变更」同源。RULE-057 §2 的「纵向小闭环」已并入本文件 §3。

## YAGNI（You Aren't Gonna Need It）

- 不要为"将来可能用到"的场景预先构建抽象、配置或扩展点。
- 只实现当前需求明确要求的范围；遇到"以后可能要"的诉求，先记录为待办，不写代码。
- 与 `rules/collaboration.md` 的「最小变更」准则同源：以最小必要改动满足需求。
- **不为并行而并行**：任务未自然可拆成互不依赖的子任务时，不要为了"用上子智能体"而拆——
  并行是执行方式的选择，不是拆任务的动机（见 `rules/collaboration.md` §2.5「最大并行度子智能体执行」）。

## 纵向小闭环（并入 RULE-057 §2）

比起一次设计十几个模块，更有效的是不断完成小的端到端闭环。每完成一个纵向闭环，都会同时学习前端、后端、权限、数据、测试和用户体验。

### 示例闭环

```
用户登录 AI
→ 授权打开 QMS 页面
→ 只读一条偏差记录
→ 生成证据快照
→ AI 形成分析草稿
→ 用户导出
→ 全程有权限控制和审计日志
```

### 每完成一个纵向闭环，逐步增加

| 阶段 | 新增内容 | 同时学习 |
|---|---|---|
| 第 1 闭环 | 登录→授权→只读记录→证据快照→AI 草稿→导出 | 前端、后端、权限、数据、测试、用户体验 |
| 第 2 闭环 | 授权撤销和会话过期 | 会话生命周期、Token 失效策略 |
| 第 3 闭环 | 敏感字段脱敏 | 数据分级、脱敏策略、审计边界 |
| 第 4 闭环 | 断线恢复和失败重试 | SSE/WebSocket 重连、幂等重试、超时控制 |
| 第 5 闭环 | 多系统信息一致性检查 | 分布式一致性、Outbox 模式、补偿事务 |
| 第 6 闭环 | 草稿导入 QMS 的受控接口 | 写操作审计、人工确认、事务边界 |

### 禁止行为

- ❌ 只研究架构图或单独写工具函数，不跑端到端闭环
- ❌ 一次性设计十几个模块，再逐一实现（长期搭架构）
- ❌ 跳过"只读记录"直接做"AI 生成草稿"（跳级导致原理理解断层）

## 与 TDD 的衔接

- 测试驱动开发（RED→GREEN→REFACTOR）见 `skills/test-driven-development`。
- YAGNI 与 TDD 互补：TDD 约束"写多少测试"，YAGNI 约束"写多少生产代码"。
- 纵向小闭环与 TDD 互补：每完成一个闭环即写对应测试，闭环即验证单元。

## 范围纪律检查清单

- [ ] 本次改动是否超出需求范围？
- [ ] 是否引入了未被任何当前调用方使用的接口/参数/配置？
- [ ] 是否可用现有能力组合替代新增代码？
- [ ] 是否已完成至少一个纵向小闭环（端到端可运行）？
