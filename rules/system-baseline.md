# 建立可验证的系统现状基线 (System Baseline)

> **本文件落实**: RULE-058（系统现状基线）
>
> 核心理念：AI 参与开发后，代码、架构意图、运行配置和文档可能分别演进，旧文档中常同时存在“已删除方案、当前方案、未来设想”。不要先逐篇整理旧文档，而应先建立一份**可验证的系统现状基线**。

---

## 1. 先区分四个“基线”（RULE-058.1）

“最新现状”至少包含四件事，不能只看 Git 最新提交：

| 基线 | 要回答的问题 |
|------|-------------|
| **代码基线** | 当前分支实际实现了什么？ |
| **运行基线** | 测试/生产环境实际部署的是哪个提交、配置和模型？ |
| **数据基线** | 当前数据库表、知识库、提示词、工具和权限配置是什么？ |
| **设计意图** | 哪些是最新确定方案，哪些只是历史试验？ |

**Git 最新提交不等于线上现状，设计文档也不等于实际运行行为。** 不要仅凭文档中的“最新”“V2”“Final”“Final2”判断现状。

---

## 2. 第一步：锁定当前代码基线（RULE-058.2）

在仓库执行：

```powershell
git status
git worktree list
git branch --show-current
git rev-parse HEAD
git log -15 --date=short --pretty=format:"%h %ad %s" --date=short
git diff --stat origin/main...HEAD
```

同时确认：

- 当前所在 worktree 和分支；
- 是否基于最新 `origin/main`；
- 是否有未提交修改；
- 是否有多个 worktree 分别保存不同试验；
- 哪些修改已合并、哪些只是本地试验；
- 最近一次可正常运行、通过测试的提交是哪一个。

建议给当前确认可用的版本建立一个明确基线，例如：

```text
系统现状基线：2026-11-09
代码提交：<commit>
前端版本：
Worker版本：
数据库迁移版本：
提示词版本：
知识库版本：
验证时间：
验证人：
```

## 3. 用一条真实链路还原系统（RULE-058.3）

不要先通读所有文档。选择一条最重要的业务链路，实际走一遍：

```text
用户登录 AI
→ 发起 QMS 读取请求
→ 用户授权并登录 QMS
→ 内容浏览器读取记录
→ 生成证据快照
→ AI 分析并生成草稿
→ 用户导出
→ 查看审计日志
```

沿着代码记录：

| 项目 | 需要查清的内容 |
|------|---------------|
| 前端入口 | 页面、按钮和实际请求地址 |
| API 入口 | 哪个路由接收请求 |
| 身份权限 | 使用哪套账号，如何识别用户和租户 |
| 授权 | QMS 登录、会话、有效期和撤销如何处理 |
| 内容浏览器 | 哪些工具可读，是否默认只读，是否存在写能力 |
| 数据保存 | 原始内容、快照、哈希、草稿分别保存在哪里 |
| AI 链路 | 使用哪个模型、提示词、工具和工作流 |
| 流式输出 | 前后端事件类型、完成和失败状态 |
| 审计 | 哪些操作有日志，敏感内容是否被记录 |
| 测试 | 当前有哪些自动化测试，最近一次是否通过 |

把结果写成一张**真实调用链图**。这一步比阅读几十份历史设计文档更容易了解系统。

## 5. 以后每次 AI 辅助修改都留下最小记录（RULE-058.5）

每次让 AI 完成一轮开发后，不只保存代码，同时更新三项：

### 5.1 变更摘要

```text
本次目标：
实际修改文件：
改变了什么行为：
数据库或配置是否变化：
API 是否兼容：
新增风险：
如何验证：
回滚方式：
```

### 5.2 架构决策记录（ADR）

只有重要架构变化才写，一页以内：

```text
决策：
为什么修改：
旧方案的问题：
备选方案：
最终选择及代价：
废弃了哪些旧设计：
```

### 5.3 验证证据

至少保留：

- 运行的测试命令；
- 测试通过或失败结果；
- 关键页面或接口验证；
- 尚未验证的事项；
- 对应提交号。

**“AI 说已经完成”不算现状证据，成功运行的测试、构建结果和实际操作记录才算。**

## 6. 最实用的一天恢复顺序（RULE-058.6）

如果时间有限，可以按这个顺序执行：

| 步骤 | 动作 | 产出 |
|------|------|------|
| 1 | **冻结继续升级**，先确定当前代码、部署和配置基线 | 代码基线确认 |
| 2 | 选择一条核心链路，实际跑通并记录 | 真实调用链图 |
| 3 | 完成“能力、路由、提示词、数据表”四份清单 | 四份清单 |
| 4 | 建立《系统现状》作为唯一入口 | `docs/00-系统现状.md` |
| 5 | 把历史文档标记为“归档/设计稿/已实施/未实施” | docs/ 目录整理 |
| 6 | 对核心链路做一次真实验证，并记录验证日期 | 验证证据 |
| 7 | 以后每次重要修改，同时更新现状文档和变更记录 | 持续更新 |

最终你要达到的状态不是“所有文档都整齐”，而是任何时候都能在十分钟内回答：

> **现在运行的是哪一版、数据从哪里来、请求经过哪些模块、哪些能力已经验证、最近改了什么、还有哪些没有完成。**

## 7. 检查清单（RULE-058.7）

建立系统现状基线前后，必须完成：

- [ ] `git status`、`git worktree list`、`git rev-parse HEAD` 已执行并记录
- [ ] 当前分支是否基于最新 `origin/main` 已确认
- [ ] 最近一次可正常运行、通过测试的提交已锁定
- [ ] 一条真实业务链路已实际走通并记录调用链图
- [ ] `docs/00-系统现状.md` 已建立，包含基线日期、Commit、部署版本、迁移版本、提示词版本、知识库版本
- [ ] 四个基线（代码/运行/数据/设计意图）各自的现状已梳理
- [ ] 历史文档已按“归档/设计稿/已实施/未实施”分类标记
- [ ] 变更摘要、架构决策记录、验证证据三项机制已启用

## 8. 反模式（禁止）

| 反模式 | 说明 | 对策 |
|--------|------|------|
| **以文档为现状** | 读设计文档当作了解系统，不验证实际运行行为 | 先走真实链路，再读文档（§3） |
| **Git 等于现状** | 认为 `git rev-parse HEAD` 就是线上运行版本 | 区分代码基线与运行基线（§1） |
| **全量文档整理** | 先逐篇整理所有旧文档，耗时且易遗漏 | 先建立 `00-系统现状.md` 唯一入口（§4） |
| **混淆历史方案** | 不区分“已删除、当前方案、未来设想”，导致误读 | 四个基线分别梳理，archive/ 只读归档（§4.1） |
| **AI 完成即算完** | 只保存代码，不更新变更摘要和验证证据 | 每次 AI 辅助修改后更新三项记录（§5） |

## 9. 与现有规则的关系

本规则与 `rules/collaboration.md`（设计文档约定、即时验证）、`rules/directory-structure.md`（RULE-053，目录结构判定）、`rules/dev-learning-loop.md`（RULE-057，开发中进步闭环）互补。建立系统现状基线是 RULE-057 中“复盘并沉淀”步骤的前置条件：没有基线，无法判断“之前怎么做、现在是什么、以后该怎么改”。
