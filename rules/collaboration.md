# AI 代理协作约定 (Collaboration Rules)
> **本文件落实**: RULE-001（创造性工作前必须触发 brainstorming）、RULE-002（设计文档未批准前禁止写代码）、RULE-014（设计文档输出前必须自检）
>
> **适用边界（v1.2.0，ADR-006）**：RULE-001 / RULE-002 按下文「分级设计门禁」的 L0–L3 级别适用——L0/L1 免设计文档与审批，不触发强制 brainstorming；仅 L2/L3 走完整链路。顶层"必须"不再是无差别强制。

> 本节约定贯穿全部工作流程，是所有 AI 代理行为的基准准则。

## 2.1 基础行为准则

| 序号 | 准则 | 说明 |
|------|------|------|
| 1 | **先读后改** | 修改任何文件前，必须先读取相关文件确认现有逻辑 |
| 2 | **思考先行** | 复杂修改前，先用 1-2 句话描述思路 |
| 3 | **最小变更** | 每次修改保持最小化，不做无关联的重构 |
| 4 | **即时验证** | 每完成一个函数/组件/接口（逻辑单元）立即运行相关测试 |
| 5 | **进度汇报** | 每完成一个计划任务，向用户报告进度 |
| 6 | **异常暂停** | 遇到计划外问题，暂停并报告，不擅自修改 |
| 7 | **栈感知** | 开始工作前必须先读取项目的 `tech-stack.md`，按其定义的技术栈执行 |
| 8 | **并行优先** | 任务可拆成互不依赖的子任务时，**以当前最大并行度派发子智能体**，不串行等待（判据与边界见 §2.5） |

## 2.2 设计文档约定

| 序号 | 约定 | 说明 |
|------|------|------|
| 9 | **三合约完整** | 设计文档必须包含完整的 HOTL 三合约（Intent / Verification / Governance） |
| 10 | **自检通过** | 设计文档输出前必须自检：约束完整性、验收标准清晰度、实现泄漏检查 |
| 11 | **实现泄漏禁令** | 设计文档中禁止出现行号引用、>10 行代码块、>=6 个 flag 的密集命令行 |
| 12 | **审批门禁** | 设计文档经用户明确批准后方可进入 `writing-plans` 阶段 |
| 13 | **规格优先（RULE-055）** | L2/L3 任务的实现依据是 `docs/tasks/<id>/spec.md`：WHAT/WHY 与编号需求在 spec，HOW 全在 plan。**spec 与设计文档同批审批**（RULE-002 门禁覆盖 spec，不是新增审批），未批准不得写代码 |
| 14 | **规格随代码同步（RULE-055 §4）** | 改代码行为 → 同 PR 更新对应 FR 或验收场景；commit 记 `spec:<slug>@v<N>`；漂移由 `spec-clarity-gate.mjs` 判 FAIL |
| 15 | **澄清不猜（RULE-055 §1.3）** | 关键分歧显式标 `[NEEDS CLARIFICATION]`（每份 spec ≤3 个），有遗留不得进入 plan / coding |

## 2.3 用户批准机制

| 命令 | 触发场景 | 执行动作 |
|------|----------|----------|
| `/approve design:<id>` | 用户确认设计文档通过 | 标记设计文档为已批准，自动触发 `writing-plans` |
| `/reject design:<id> [原因]` | 用户要求修改设计 | 返回 `brainstorming` 阶段，携带拒绝原因 |
| `/approve plan:<id>` | 用户确认执行计划 | 标记计划为已批准，允许进入 `executing-plans` |
| `/pause` | 用户要求暂停工作 | 保存当前状态，等待 `/resume` 或新指令 |
| `/resume` | 用户要求恢复工作 | 从上次暂停点继续执行 |

> **默认审批方式**：用户在对话中明确回复"批准"、"同意"、"通过"、"可以开始"等关键词，即视为设计文档或计划已获批准。无需特定斜杠命令。

## 2.4 AI 编码协作专项约定

### 设计文档中的 AI 辅助标注

当设计文档中包含 AI 生成的内容时，必须明确标注：

| 标注项 | 说明 | 示例 |
|-------|------|------|
| **AI 辅助标记** | 标注哪些部分由 AI 生成 | `[AI辅助]`、`[AI-generated]` |
| **人工审查确认** | 标注已人工 Review 的关键部分 | `[人工审查]` |
| **边界条件清单** | 列出所有考虑的边界条件 | 见下方模板 |
| **复杂度分析** | 标注时间/空间复杂度 | `O(n log n)` |
| **风险标注** | 标注潜在风险点 | `[风险：并发]` |

### 设计文档模板增强

```markdown
## 边界条件处理

| 场景 | 处理方式 | AI 生成 | 人工确认 |
|-----|---------|--------|---------|
| 空数组输入 | 返回空结果 | [AI辅助] | [人工审查] |
| 超大输入 | 分批处理 | [AI辅助] | [人工审查] |
| 类型错误 | 抛出 AppException | [AI辅助] | [人工审查] |
| 并发访问 | 乐观锁 | [AI辅助] | [人工审查] |

## 复杂度分析

- 时间复杂度: O(n log n)
- 空间复杂度: O(n)
- 瓶颈分析: [说明]

## 风险评估

| 风险类型 | 风险描述 | 缓解措施 |
|---------|---------|---------|
| 性能 | 大数据量可能超时 | 分页 + 缓存 |
| 安全 | SQL 注入风险 | 使用 ORM |
| 并发 | 竞态条件 | 乐观锁 |
```

### 爆炸半径评估（Blast Radius）

| 半径级别 | 波及文件数 | 执行策略 |
|----------|-----------|----------|
| 微型 | 1-2 个 | 直接执行 |
| 小型 | 3-5 个 | 可按依赖拆为子任务，逐个验证 |
| 中型 | 6-10 个 | 建议拆分并明确验证点 |
| 大型 | > 10 个 | 拆分为多个独立功能点，分批执行 |

> **决策原则**：改动越大，提交隔离性与可回滚性越差。优先按依赖拆分为可独立验证的小批次。**判定依据是依赖与风险，不是预估耗时。**

### 任务拆解粒度控制

**黄金法则**：单个子任务聚焦**清晰的逻辑边界**（一个函数/组件/接口/用例），以"改动边界清晰、可独立验证、可独立回滚"为准。**不设行数阈值**——行数不是可验证的拆分依据，按依赖关系与验证点拆分即可。

### 2.5 最大并行度子智能体执行（并行优先）

> **原则**：任务能拆成多个**互不依赖**的子任务时，**必须并行派发子智能体**，不得串行等待；
> 并行度取**当前环境可用的最大并行度**，不做保守收缩。串行只在存在真实依赖时使用。

**判据（先拆后派）**：

1. 先按「任务拆解粒度控制」把任务拆成可独立验证的逻辑单元；
2. 无依赖关系的子单元 → **并行**；有依赖关系的 → **按依赖分层，同层并行**；
3. **共享写区不并行**：同一文件 / 同一目录 / 同一 worktree，以及共享文件独占区（`wrangler.toml`、`package.json`、`deploy/deploy.ps1`、`.env*`）**只允许一个 Agent 写入**，其余只读取证。
4. **任务级互斥（同 spec 不并行，v1.5.0 增补）**：同一 spec / 同一主题 / 同一验收目标的任务，**并行实例 ≤1**；派发前必须检索在途分支与任务清单（`git branch` / 任务板 / 收工纪要），命中即串行等待或合并派发。产物查重（RULE-053 §3.5）只挡「文件重复」，挡不住「四个代理各写一遍同一门禁」——2026-11-13 qms 同一分钟 4 个同题提交 + 4 个同题合并（8 个噪音提交进主干）实证。

**三类典型并行**：

| 场景 | 并行方式 |
|------|---------|
| 跨文件只读取证（审计、搜索、影响面扫描、现状盘点） | 全部并行，各子 Agent 独立上下文 |
| 多模块独立实现（文件集互不重叠） | 按目录切分并行，每个子 Agent 自带验证动作 |
| 同一改动的多维度独立核查 | 并行多视角审查，汇总后合并结论 |

**工具映射（DeepSeek Harness）**：

| 工具 | 用途 | 何时选 |
|------|------|--------|
| `subagent` | 独立上下文的子任务（一次性、边界清晰、无需共享工作区） | 只读取证、独立实现、独立核查 |
| `subagent_fork` | 继承当前对话上下文的后续分析 | 需要基于既有对话继续的分析/复核 |
| `spawn_teammate` | 持久队友：与主 Agent **共享文件系统** | 多步协作，各 Agent 负责独立目录 |
| `workflow` | 脚本化大规模扇出编排 | **仅在用户显式要求大规模多 Agent 编排时使用** |

**边界（不得以并行之名降低质量）**：

- 子 Agent **各自必须带验证证据**——并行不豁免验证（RULE-004 完成声明 / RULE-028 Linter）；
- 子 Agent 之间的结论用**文件**传递（写进各自负责的落点），不靠"口头对齐"；
- 共享文件的写入冲突 → **串行收口**，由一个 Agent 统一合并；
- 不可并行的前置（读码定位、方案判定、基线锁定）**先串行完成**，再并行执行；
- 并行不得突破工作区隔离与共享文件独占区纪律，也不得为"看起来更快"而降低门禁强度。

> **与 YAGNI 的关系**（见 `rules/engineering-principles.md`）：**不为并行而并行**——单文件、单函数的改动不需要派子 Agent；
> 并行是**任务已经自然可拆**时的执行方式选择，不是拆任务的动机。

### 2.6 跨 AI 任务台账（多工具并发开发 · 文件即真源）

> **适用**：同一工作区/仓被多个 AI 工具（Claude Code、Trae、Qoder、CodeBuddy 等）并发开发时。多仓容器型工作区（如 example-workspace 四仓 + `outputs/`）台账落点见 `outputs/任务台账/README.md`，单仓项目可落 `docs/tasks/` 或仓根 `tasks/`（RULE-053 落点表）。

**三纪律**：

| # | 纪律 | 内容 | 反什么 |
|---|------|------|--------|
| 1 | **开工先查台账** | 认领任务前先查任务索引有无同目标在途任务（同 spec / 同主题 / 同验收目标），命中即串行等待或合并派发 | 两个 AI 重复做同一任务 |
| 2 | **收工必写台账** | 会话结束前更新任务文件进展日志与状态；**AI 不写台账 = 等于没干** | 状态散在私有会话，他人无法接手 |
| 3 | **一任务一 worktree** | 每个进行中任务独立 worktree，任务 ID ↔ worktree 名映射登记在任务文件认领记录 | 并发写同一工作树冲突 |

**五段契约**（任务文件必备）：frontmatter（机器可读）· 目标与验收（可验证判据）· 写范围 · 认领记录 · 进展日志（append-only）+ 交接状态。模板与看板脚本见 `outputs/任务台账/`。

> **与 §2.5 任务级互斥的关系**：§2.5 的「同 spec 并行实例 ≤1、派发前检索在途」是**执行时**互斥；本节纪律 1 是**认领前**查重（RULE-053 §3.5 挡「文件重复」、§2.5 挡「并行重复」，本节挡「认领重复」）。三者互补，不重复判。

### 2.7 文档同步纪律（关键结构改动必带 · v1.7.0 增补）

> **适用**：工作区级项目参考文档真源 `docs/wiki/`（工具无关，所有 AI 工具经 `AGENTS.md` §1 统一发现）。`.qoder/repowiki` 仅是 Qoder 生成视图，**不以此为准**。

**纪律**：

| # | 纪律 | 内容 | 反什么 |
|---|------|------|--------|
| 1 | **关键结构必带文档同步** | 改动 A/B 仓 Supabase 迁移、C 仓 `schema.sql`、路由契约（`worker/src/config/routes.ts`、`worker/src/products/data.ts`）、插件能力清单等关键结构时，任务**验收项必须包含「更新 `docs/wiki/` 对应文档」** | 文档漂移、跨工具读到过时参考 |
| 2 | **未同步不得关闭** | 未更新对应 `docs/wiki` 文档的任务，不得标记已关闭 | 「AI 自称完成」但文档滞后 |

> **与 §2.6 的关系**：文档同步作为 §2.6 五段契约「目标与验收」的强制验收项之一，随任务文件一并登记与核对。

### 分级设计门禁（Tiered Design Gate）

> 目的：避免"所有改动一律要求设计文档 + 审批"造成不必要的流程开销。按改动规模与风险分级，**小改动免审批、小风险免设计文档**，只有达到阈值才强制走完整 `brainstorming` → 设计文档 → 审批链路。

| 门禁级别 | 判定条件 | 设计文档要求 | 审批要求 | 对应执行模式 |
|----------|----------|-------------|----------|--------------|
| **L0 免门禁** | 单文件、样式调整、文档更新、Bug 修复（单文件）、依赖升级 | 无需 | 无需 | 模式 A 完全自主 |
| **L1 轻量门禁** | 3-5 文件、无架构影响的新增功能、多文件 Bug 修复 | 可选（≤1 页敏捷式设计） | 无需 | 模式 B 轻量 |
| **L2 标准门禁** | >5 文件、涉及 API/DB Schema 变更、新增模块 | 必须（7 章标准设计文档 + HOTL 三合约；**spec 已覆盖的章节不重复写**，见下方防瀑布纪律） | 必须 | 模式 B 规划后执行 |
| **L3 强制门禁** | 架构调整、跨模块重构、安全/认证/隐私/计费相关、性能优化 | 必须 | 必须（高风险自动人工门禁） | 模式 C 协作编排 |

**各门禁级别的规格（spec）要求**（ADR-008 / RULE-055 §6）：

| 门禁级别 | 规格要求 | 落盘位置 |
|----------|----------|----------|
| L0 | 无（对话内说明即可） | — |
| L1 | 对话内轻量规格：意图 + 范围 + 一条验收，**不落盘** | — |
| L2 | 落盘完整规格（`templates/spec/spec-template.md` 骨架） | `docs/tasks/<id>/spec.md` |
| L3 | 规格 + `design.md`（含 Constitution Check 违规模块） | `docs/tasks/<id>/spec.md` + `design.md` |

> L2/L3 的规格随设计文档**同批审批**（RULE-002 门禁一次覆盖两份产物），批准后进入 `writing-plans`。
> L0/L1 不落盘规格属正常态——`spec-clarity-gate.mjs` 对无 `docs/tasks/**/spec.md` 的仓只告警不 FAIL。

**防「Markdown 瀑布」硬纪律**（ADR-008 给自己上的约束，L2 尤其适用）：

| # | 纪律 | 反什么 |
|---|------|--------|
| 1 | spec 已写 WHAT/WHY 与编号需求，**设计文档就只写系统形态与选型**——四份文档里的"功能列表 / Scope / 验收标准"章节**允许留空并指向 `spec.md`**，不许两边各写一份 | spec 变成第二份设计文档 |
| 2 | **不要求每个 L2 都产四份设计文档**：按需拆分见 `rules/workflow-core.md` §6.1.2（纯后端可跳过 `ui-wireframe`；纯前端可跳过 `architecture` + `database-schema`；MVP 四文档可合并为单份 `design.md`） | "必须有四份"的形式主义 |
| 3 | **L2 合理产物上限**：1 份设计文档（按需 1–2 份）+ `spec.md`（≤200 行）+ `plan.md` + `tasks.md`。接近上限时先怀疑**是否在重复描述同一件事**，而不是加快手速 | 8 个文件 1300 行的实证反例 |

**免审批边界（L0/L1）判定规则**：
- **不触碰** `schemas/`、`tech-stack.md`、`AGENTS.md`、`rules/` 等契约/规则文件 → 通常可免审批。
- **不涉及** 数据库表结构、外部 API 契约、权限模型 → 即使跨 3-5 文件仍可走 L1 轻量门禁。
- **安全/认证/隐私/计费** 相关需求无论规模一律升至 L3（RW：`rules/priority-system.md` 风险等级为 high 自动要求人工门禁）。

**门禁触发检查点**：
1. **任务启动时**：按上表判定初始门禁级别，声明"本次为 Lx 门禁"。
2. **执行中升级**：若改动超出初始判定（如从 3 文件扩到 8 文件、途中发现需改 DB Schema），立即暂停并升级门禁级别，补齐对应设计文档与审批。
3. **禁止降级**：不得因"快做完了"而反向降级跳过审批。

> 门禁秒查：`L0 单文件免审` → `L1 3-5 文件无架构影响免审` → `L2 超阈值须设计文档+审批` → `L3 架构/安全强制人工门禁`。

### 上下文投喂策略（Context Feeding）

**必须投喂（P0）**：
- 项目技术栈文件 `tech-stack.md`
- 同类功能的已有实现（参考代码）
- 框架版本约束

**强烈建议（P1）**：
- ESLint / Prettier 配置
- 命名约定和接口返回格式规范
- 公共工具函数库位置
- 错误处理中间件示例

**有效补充（P2）**：
- 截图（UI 调整时）
- 目录结构树
- 依赖版本清单

### 负向约束

> **负向约束优先级高于正向指令**：当正向指令与负向约束冲突时，以负向约束为准。负向约束定义了不可逾越的边界，AI 必须在边界内执行正向指令。

> **v1.2.0 说明（ADR-006）**：原"Vibe Coding 约束"（一次一事、读懂再用、小步提交、验证先行、增量迭代）面向"人在聊天框逐条下 prompt"的场景，已删除。其有效内核已由 §2.1「即时验证」「最小变更」与 Git 规范覆盖。自主 Agent 可在"证据充分、可独立验证"的前提下批量推进。
