# 技术债务管理

> 基于"阶段性偿还优于每次完美"的实践原则，平衡迭代速度与代码质量。

## 核心策略：20% 规则

每 5 个功能迭代周期，留出 1 个周期专门用于技术债务偿还。

```
迭代 1-4: 功能开发（允许"快速但略脏"）
迭代 5:    重构 + 优化 + 文档补齐
```

## 债务类型与处理方式

| 债务类型 | 示例 | 处理时机 | 方式 |
|----------|------|----------|------|
| 代码重复 | 复制粘贴的相似逻辑 | 重构迭代 | 提取公共函数/组件 |
| 死代码 | 未使用的导入/变量/函数 | 重构迭代 | `knip` / `eslint` 自动清理 |
| 慢查询 | 无索引的数据库查询 | 发现时 | 立即添加索引（低风险） |
| 大文件 | 超过 300 行的组件/模块（与 coding-standards 阈值一致） | 重构迭代 | 按职责拆分 |
| 测试缺失 | 核心路径无覆盖 | 重构迭代 | 补全关键路径测试 |
| 依赖老旧 | 过期版本有安全漏洞 | 发现时 | 立即升级（高风险） |

## 重构日清单

**前端 / TS 项目：**
- [ ] 运行 `jscpd` 检查重复代码
- [ ] 运行 `knip` 清理死代码
- [ ] 运行 `eslint` 检查弃用 API

**Python 项目（对等工具）：**
- [ ] 运行 `jscpd`（`--languages python`）检查重复代码
- [ ] 运行 `vulture` / `ruff check --select F401,F841` 清理死代码与未用变量
- [ ] 运行 `ruff check` 检查弃用 API（`UP` 规则组）

**通用：**
- [ ] 检查可合并的重复 API 路由
- [ ] 拆分超过 300 行的文件
- [ ] 更新关键依赖版本
- [ ] 补全复杂逻辑的注释和测试
- [ ] 检查并优化慢查询

> **关键原则**：先快速验证功能，再阶段性优化。不要追求每个提交都完美，但要确保债务不会累积到无法偿还。
