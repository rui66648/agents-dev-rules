# 开发中进步的闭环规则 (Developer Learning Loop)

> **本文件落实**: RULE-057（开发中进步闭环）
>
> 核心理念：在开发中进步，关键不是“看得更多”或“做完更多功能”，而是形成这个闭环：
>
> > **带着问题做项目 → 独立解决具体问题 → 理解背后原理 → 复盘并沉淀 → 用更复杂的问题验证。**
>
> 本规则适用于所有自主 Agent 与人工开发者，尤其针对 AI＋QMS、企业内容浏览器、Supabase/Qdrant 等混合栈项目。

---

## 1. 每个开发任务都带一个学习目标（RULE-057.1）

不要只写“完成 QMS 授权登录”，同时明确这次要弄懂什么。

### 1.1 任务与学习目标绑定

| 开发任务 | 应学会的内容 |
|---|---|
| 企业内容浏览器 | Cookie 隔离、会话绑定、权限范围、CSRF/XSS、凭据保护 |
| Supabase 数据层 | 表设计、事务、RLS、幂等、事务与 Outbox |
| Qdrant 检索 | Embedding、过滤、权限、召回质量、索引重建 |
| Agent 工具调用 | 状态机、超时、重试、停止条件、错误分类 |
| 前端流式输出 | SSE、事件序号、断线恢复、取消、重复事件处理 |
| AI 草稿生成 | 证据绑定、权限边界、敏感信息处理、人工确认 |

### 1.2 每完成一项，必须回答四个反问

每完成一项功能，不只是打勾“功能做完了”，还要回答：

| 反问 | 用途 |
|---|---|
| 为什么这样设计？ | 理解设计意图，避免盲目模仿 |
| 有什么替代方案？ | 知道取舍，不陷入“只有这一种做法”的思维定势 |
| 当前方案最容易在哪里出错？ | 为排错和测试预置雷达 |
| 如果用户量或数据量扩大十倍，会先在哪里出问题？ | 为架构演进预留观察点 |

### 1.3 检查清单（每项任务完成前）

- [ ] 任务说明中已写明“本次要弄懂什么”
- [ ] 四个反问都已有文字答案（可留在 commit message 或任务笔记中）
- [ ] 能独立解释该功能的数据流向和关键边界
- [ ] 能说出该功能最可能的失败模式

## 2. 用“纵向小闭环”学习，避免长期搭架构（RULE-057.2）

比起一次设计十几个模块，更有效的是不断完成小的端到端闭环。**本节已并入 `rules/engineering-principles.md` §3**，包括：

- 示例闭环（登录→授权→只读记录→证据快照→AI 草稿→导出）
- 六个递进阶段（授权撤销→会话过期→脱敏→断线恢复→一致性检查→受控写入）
- 禁止行为（只研究架构图、一次性设计十几个模块、跳级做 AI 草稿）

> `engineering-principles.md` 是纵向小闭环的唯一真源，`dev-learning-loop.md` 不再重复维护闭环细节。执行 RULE-057.2 时以 `engineering-principles.md` §3 为准。

## 3. 把排错当作最重要的学习机会（RULE-057.3）

遇到问题不要只记录“已修复”，建议留下五件事：

### 3.1 排错五件事模板

```
现象：实际发生了什么？
预期：本来应该发生什么？
定位：如何缩小问题范围？
根因：代码、配置、数据、权限还是理解错误？
修复：修改了什么？
预防：增加什么测试或校验可以避免复发？
```

### 3.2 以“AI 读取了错误的 QMS 记录”为例的深挖

不要只修一个 ID 映射，还应继续问：

- 授权会话是否绑定用户？
- 页面记录 ID 是否可信？
- 服务端是否重新校验权限？
- 是否有跨用户会话串用的测试？
- 是否需要增加一条永久回归用例？

### 3.3 检查清单

- [ ] 现象与预期都已文字化
- [ ] 定位路径已记录（如何缩小到具体文件/行）
- [ ] 根因已判定（代码/配置/数据/权限/理解错误，五选一或多选）
- [ ] 修复改动已提交，并关联回归用例
- [ ] 预防措施已落地（测试用例、断言、校验、文档）

## 4. 使用 AI 辅助开发，但不要替代思考（RULE-057.4）

推荐采用以下节奏：

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 先自己写清问题、约束和预期结果 | 问题陈述 |
| 2 | 让 AI 给方案，并要求说明取舍和适用条件 | 方案对比 |
| 3 | 不直接复制大段代码，先理解数据流和关键边界 | 数据流图或文字说明 |
| 4 | 自己实现最小版本，再让 AI 做代码审查 | 最小可执行版本 + Review 记录 |
| 5 | 主动询问：什么情况下会失败？有没有更简单的实现？哪些假设未被验证？应该补哪些测试？ | 风险清单 + 测试计划 |
| 6 | 最后脱离 AI，自己解释一遍设计并复述核心代码逻辑 | 能够口头讲透的设计说明 |

### 4.1 判断标准

如果一段代码你只能运行、不能解释，出现错误也无法定位，那它还没有真正转化为你的能力。**不得将“能运行”作为任务完成的判据。**

## 5. 通过阅读源码提升，而不是只读教程（RULE-057.5）

建议每次选择一个小问题深入源码。例如研究提示词稳定性，可沿着一条真实调用链阅读：

```
请求入口
→ 路由
→ Prompt 拼装
→ 工具选择
→ 模型调用
→ 工具结果
→ 最终答案
→ 日志和 SSE 事件
```

### 5.1 阅读时记录

- 输入和输出是什么；
- 状态保存在哪里；
- 谁负责权限校验；
- 失败时如何结束；
- 哪些内容会进入模型上下文；
- 修改此处会影响哪些模块。

### 5.2 纪律

比“泛读很多框架”更有效的方法，是围绕一个真实问题追踪完整链路。**每次阅读源码必须绑定一个正在排查或实现的具体问题，禁止无目标泛读。**

## 6. 建立个人知识资产（RULE-057.6）

每完成一个功能，不必写长文，留下半页即可：

### 6.1 半页笔记模板

```
本次解决的问题：
我原来的理解：
实际验证后的结论：
最关键的一个原理：
踩过的坑及原因：
仍然不理解的问题：
下次可以复用的代码、测试或方法：
```

### 6.2 定期整理成知识库

- `架构决策记录`（ADR）
- `常见问题与排查手册`
- `安全与权限检查清单`
- `测试反例集`
- `技术选型与放弃原因`
- `性能与成本实测记录`

这些内容比收藏大量文章更能形成自己的能力。

## 7. 适合当前项目的学习顺序（RULE-057.7）

建议按以下顺序推进：

| 阶段 | 学习内容 | 对应项目模块 |
|---|---|---|
| 1 | 先掌握基础闭环：API、数据库、权限、错误处理和测试 | QMS worker、Supabase |
| 2 | 再做 AI 与 QMS 的最小只读授权闭环 | 登录→授权→只读记录 |
| 3 | 加入安全测试：越权、会话串用、敏感字段泄露、提示词注入 | Qdrant 检索、AI 草稿 |
| 4 | 用真实脱敏案例验证 AI 建议是否有价值 | 证据快照、人工确认 |
| 5 | 最后再优化多 Agent、复杂图谱、自动化写操作等高级能力 | Agent 工具调用、知识图谱 |

### 7.1 每周三问

每周可以问自己三个问题：

1. 本周我真正弄懂了哪个以前只会调用的概念？
2. 我修复或预防了哪一类过去不会发现的问题？
3. 如果现在重新设计，我会删掉哪些不必要的复杂度？

### 7.2 进步的明显标志

**进步的明显标志，不是掌握的术语越来越多，而是能用更简单的方案解决真实问题，并能解释每个设计选择的代价和边界。**

## 8. 检查清单与反模式（RULE-057.8）

### 8.1 任务完成前检查清单

| 序号 | 检查项 | 判据 |
|------|--------|------|
| 1 | 任务说明中是否已写明学习目标 | 有文字说明 |
| 2 | 四个反问是否都有答案 | 每个反问都有文字回应 |
| 3 | 是否完成了纵向小闭环 | 端到端可运行，有权限和审计 |
| 4 | 排错是否留下五件事 | 现象/预期/定位/根因/修复/预防完整 |
| 5 | AI 辅助代码是否已自己解释一遍 | 能口头讲透核心逻辑 |
| 6 | 是否留下半页知识资产笔记 | 符合 §6.1 模板 |
| 7 | 本周三问是否已思考 | 三个问题都有答案 |

### 8.2 反模式（禁止）

| 反模式 | 说明 | 对策 |
|--------|------|------|
| **只打勾不复盘** | 功能做完了就算完成，不回答四个反问 | 强制在任务笔记中填写四个反问 |
| **长期搭架构** | 一次设计十几个模块，不跑端到端闭环 | 优先完成纵向小闭环，再逐步扩展 |
| **只修表象不深挖** | Bug 只改 ID 映射，不问会话绑定、权限校验等 | 按 §3 排错五件事深挖 |
| **AI 代码不解释** | 只能运行不能解释，出错无法定位 | 按 §4 节奏，脱离 AI 自我讲解 |
| **泛读源码** | 无目标阅读大量框架源码 | 围绕具体问题追踪完整调用链（§5） |
| **不沉淀知识** | 功能做完不留笔记，零散知识无法复用 | 每项功能留半页笔记（§6.1 模板） |

### 8.3 新增规则时的自检（本规则自身的教训，2026-11-10 补）

> 起因：RULE-057 写入后跨 8 批真实任务**零触发**，诊断出五处接入层断点（见 `docs/learning/2026-11-10-rule-057-结构性失效修复.md`）。结论：**规则不是文档，是机制**——只写内容而不接入，等于存档。

新增任何一条规则时，同批检查**四件套**，缺件即视为规则未完成：

| # | 件 | 缺了会怎样 | 落点 |
|---|----|-----------|------|
| 1 | **触发入口** | Agent 永远不会加载它 | `AGENTS.md` §2 入口路由（**不是**只写 §3 速查表） |
| 2 | **产物落点** | 知道该做但不知道写在哪，写了还会被判违规 | `rules/directory-structure.md` §1 L3 落点表 + 各仓 `AGENTS.md` 产物落盘段 |
| 3 | **内容模板** | 知道要做什么但格式全凭发挥，无法批量检查 | `templates/<域>/<name>-template.md` |
| 4 | **可执行判据** | 靠自觉，漏了不可见 | `hooks/scripts/*`（能判的判）+ `hooks/configs/gate-inventory.yaml` 登记 |

> **配套两条纪律**：① 能用 Hook/Linter 确定性判的，不要只写 MD 清单（本库 §8 使用纪律）；② 判据必须**弱而诚实**——只能判「没写」就别假装能判「没学会」，否则即自造假绿（判据边界写在 `gate-inventory.yaml` 的 reason 里）。

## 9. 适用边界与分级

> **与 RULE-001 / RULE-055 的 L0–L3 同源（不重复判两遍）**：三处分级都按「改动范围 + 影响面」判定，取**同一档**即可——RULE-001 用该档决定是否强制 `brainstorming`；RULE-055 用该档决定 spec 是否落盘；本节用该档决定学习闭环强度。**唯一差异**：L1 在 RULE-055 下不落盘 spec（对话内轻量），但在本节下**必须**写明学习目标并留下 `docs/learning/` 笔记。

| 分级 | 适用 | 要求 |
|------|------|------|
| L0 | 单文件、样式调整、文档更新 | 鼓励带学习目标，不强制 |
| L1 | 3-5 文件、轻量新增功能 | 必须写明学习目标 |
| L2 | >5 文件、涉及 API/DB Schema 变更、新增模块 | 全套规则适用（四个反问、纵向闭环、排错五件事、半页笔记） |
| L3 | 架构调整、跨模块重构、安全/认证/隐私/计费 | 全套规则适用 + 必须每周回答三问 |

---

> **与现有规则的关系**：本规则与 `rules/collaboration.md`（最小变更、即时验证）、`rules/anti-patterns.md`（AI 辅助开发反模式）、`rules/testing-rules.md`（TDD）互补，不冲突。执行本规则时，若遇到与现有规则冲突，以现有铁律为准，并记录偏差。
