# /debug - 调试流程

**触发词**: "调试一下"、"排查问题"、"bug"、"报错"、"异常"

---

## 命令语法

```
/debug [symptom] [--level=app|db|infra|all] [--trace=false|true]
```

## 参数说明

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `symptom` | string | 否 | 需交互确认 | 问题症状描述，如 `500 error on login` 或 `slow query on dashboard` |
| `--level` | enum | 否 | `app` | 排查层级：`app`（应用层）、`db`（数据库层）、`infra`（基础设施层）、`all`（全栈） |
| `--trace` | bool | 否 | `false` | 是否开启全链路追踪（request_id 串联日志） |

## 触发场景

- 线上或测试环境出现异常，需要定位根因
- 本地开发时功能不按预期工作
- 性能问题（接口响应慢、页面卡顿、内存泄漏）
- 测试用例失败，需要理解失败原因
- 部署后服务不可用或行为异常
- 日志中出现 ERROR/FATAL 级别告警

## 前置条件

1. 问题可复现，或已收集到异常日志/错误信息
2. 对应环境的日志系统可访问（本地日志文件或日志平台）
3. 代码版本与问题发生时一致（或已知 commit 范围）
4. 如 `--trace=true`，应用已配置 `request_id` 注入

## 执行流程

1. **症状收集** — 确认问题现象、影响范围、首次出现时间、复现步骤
2. **假设形成** — 根据症状提出 3-5 个可能根因假设，按概率排序
3. **证据收集** — 按 `--level` 收集日志、堆栈、数据库慢查询、系统指标
4. **假设验证** — 逐一验证或排除假设，聚焦最可能的根因
5. **根因定位** — 确认根因，输出问题发生的代码位置、触发条件、影响面
6. **修复方案** — 提供修复建议或临时缓解措施（workaround）
7. **验证修复** — 执行修复后重试复现步骤，确认问题解决
8. **回归测试** — 运行相关测试，确保修复未引入新问题

## 产出物

- **问题根因分析**：根因描述、触发条件、影响范围、代码位置
- **修复方案**：推荐修复方式 + 备选 workaround
- **验证结果**：修复前后的对比验证记录
- **预防建议**：避免同类问题再次发生的措施（如增加校验、改进监控）

## 错误处理

| 常见错误 | 处理方式 |
|----------|----------|
| 问题无法复现 | 收集更多上下文（环境、数据、时间），建议增加日志后再观察 |
| 日志信息不足 | 建议提升日志级别至 DEBUG，或增加关键路径的日志埋点 |
| 根因不在应用层 | 按 `--level` 扩展排查范围，检查数据库、网络、基础设施 |
| 修复引入回归问题 | 回滚修复，重新分析根因，采用更保守的修复方案 |
| 假设全部排除 | 扩大排查范围，收集更细粒度的系统指标，或引入代码审查 |

## 示例

### 示例 1：排查登录接口 500 错误

```
/debug "500 error on /api/auth/login" --level=app --trace=true
```

**预期输出**：
- 症状：POST /api/auth/login 返回 500，约 30% 请求失败
- 根因：`user_service.authenticate()` 中未处理 `None` 返回值，导致 `AttributeError`
- 修复：增加空值检查并返回 401
- 验证：修复后 100% 请求正常

### 示例 2：排查仪表盘加载缓慢

```
/debug "dashboard loads >10s" --level=all
```

**预期输出**：
- 症状：/dashboard 接口平均响应 12s，P95 18s
- 根因：用户统计查询缺少索引，全表扫描 + N+1 查询
- 修复：添加复合索引 `(user_id, created_at)`，改用 `selectinload`
- 验证：修复后平均响应降至 200ms
