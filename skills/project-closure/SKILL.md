# Project Closure


## 负责代理

`architect` — 项目收尾由架构师代理负责，确保验收、复盘和文档归档完整。

## 何时使用

- 项目主要功能开发完成，进入验收阶段时
- 需要进行项目级复盘总结时
- 需要归档项目文档、沉淀知识时
- 项目转入维护期，需要正式收尾时

**触发关键词**: "项目收尾"、"项目验收"、"复盘"、"文档归档"、"知识沉淀"、"项目总结"

## 与其他技能的关系

```
finishing-branch (分支级收尾: 合并/PR/清理)
        ↓
ops-monitoring (运维稳定期)
        ↓
project-closure (项目级收尾: 验收/复盘/归档)
```

> **衔接规则**: `finishing-branch` 处理代码分支级别的合并和清理；`project-closure` 处理项目级别的验收、复盘和归档。前者是后者的前置条件。

## 执行流程

### Phase 1: 项目验收

**目标**: 确认交付物完整、质量达标，正式交付。

1. **交付物清单确认**

   | 交付物类别 | 具体内容 | 状态 |
   |-----------|----------|------|
   | **代码** | 源代码仓库（已合并到主分支） | [ ] 已交付 |
   | **文档** | 项目立项书、设计文档、API 文档、运维手册 | [ ] 已交付 |
   | **测试** | 测试报告、测试用例 | [ ] 已交付 |
   | **部署** | 生产环境已部署且运行正常 | [ ] 已交付 |
   | **监控** | 监控面板、告警规则已配置 | [ ] 已交付 |
   | **数据** | 数据库备份已验证 | [ ] 已交付 |

2. **验收标准核对**
   - 对照 `project-initiation` 阶段定义的成功指标
   - 对照 `test-strategy` 阶段的测试报告结论
   - 对照 `brainstorming` 设计文档的验收标准
   - 列出未达标项及处理方案

3. **验收报告**

   输出 `docs/project-acceptance.md`：

   ```markdown
   # 项目验收报告: [项目名称]

   ## 1. 验收概要
   - 项目名称:
   - 验收日期:
   - 验收人:

   ## 2. 交付物清单
   （引用上方交付物表格）

   ## 3. 成功指标达成情况
   | 指标 | 目标值 | 实际值 | 达成 |
   |------|--------|--------|------|

   ## 4. 遗留问题
   | 问题 | 严重程度 | 处理方案 | 计划完成时间 |
   |------|----------|----------|-------------|

   ## 5. 验收结论
   - [ ] 通过
   - [ ] 有条件通过
   - [ ] 不通过
   ```

### Phase 2: 项目复盘

**目标**: 总结经验教训，持续改进。

1. **复盘会议准备**
   - 收集项目全程数据：工期、Bug 数、返工次数
   - 整理关键事件时间线：里程碑、阻塞点、决策点
   - 准备复盘模板

2. **复盘四问**

   | 维度 | 问题 | 输出 |
   |------|------|------|
   | **做得好** | 哪些做得好？为什么好？ | 可复制的经验 |
   | **待改进** | 哪些做得不好？根因是什么？ | 改进措施 |
   | **意外收获** | 有哪些计划外的收获？ | 知识增量 |
   | **后续行动** | 下一步做什么？谁来做？ | Action Items |

3. **复盘报告**

   输出 `docs/project-retrospective.md`：

   ```markdown
   # 项目复盘报告: [项目名称]

   ## 1. 项目概览
   - 项目周期: YYYY-MM-DD ~ YYYY-MM-DD
   - 实际工期 vs 预估工期:
   - 团队规模:

   ## 2. 做得好（Keep）
   | 事项 | 原因 | 可复制性 |
   |------|------|----------|

   ## 3. 待改进（Problem）
   | 事项 | 根因分析 | 改进措施 |
   |------|----------|----------|

   ## 4. 意外收获（Surprise）
   ## 5. Action Items
   | # | 行动项 | 负责人 | 截止日期 | 状态 |
   |---|--------|--------|----------|------|

   ## 6. 数据回顾
   - Bug 总数: ?
   - P0/P1 Bug 数: ?
   - 返工次数: ?
   - 测试覆盖率: ?
   ```

### Phase 3: 文档归档

**目标**: 确保项目文档完整可追溯。

1. **文档完整性检查**

   | 文档类别 | 文档名称 | 路径 | 状态 |
   |----------|----------|------|------|
   | 立项 | 项目立项书 | `docs/project-initiation.md` | [ ] |
   | 设计 | 需求设计文档 | `docs/designs/*-design.md` | [ ] |
   | 设计 | 架构设计文档 | `docs/designs/*-architecture.md` | [ ] |
   | 计划 | 实施计划 | 对话中输出（不生成文件） | [ ] |
   | 测试 | 测试计划 | `docs/test-plan.md` | [ ] |
   | 测试 | 测试报告 | `docs/test-report.md` | [ ] |
   | 运维 | 运维手册 | `docs/ops-manual.md` | [ ] |
   | 验收 | 验收报告 | `docs/project-acceptance.md` | [ ] |
   | 复盘 | 复盘报告 | `docs/project-retrospective.md` | [ ] |

2. **代码仓库归档**
   - 确认所有代码已合并到主分支
   - 清理临时分支（feature/ 开头的分支）
   - 确认 Git Tag 已打版本标签
   - 确认 README.md 最终版本已更新

3. **文档版本标记**
   - 所有文档标注最终版本号
   - 标记文档状态为"已归档"
   - 移至 `docs/archive/` 目录（如适用）

### Phase 4: 知识沉淀

**目标**: 将项目经验转化为可复用的知识资产。

1. **可复用组件提取**
   - 通用工具函数/类
   - 可复用的 UI 组件
   - 通用配置模板
   - CI/CD 流水线模板

2. **经验沉淀**
   - 技术选型经验：哪些选对了，哪些选错了
   - 架构设计经验：哪些设计经受住了考验
   - 踩坑记录：避免重复犯错的清单
   - 性能优化经验：实际有效的优化手段

3. **知识分享**
   - 编写技术博客或内部 Wiki
   - 整理可分享的 PPT/技术演讲
   - 更新团队最佳实践文档

4. **更新项目记忆**
   - 将项目经验写入 `project_memory.md`
   - 更新 `user_profile.md` 中的技能标签
   - 标注可复用于未来项目的模式

### Phase 5: 项目收尾确认

**最终检查清单**:

- [ ] 交付物全部确认
- [ ] 验收报告已签署
- [ ] 复盘报告已完成
- [ ] Action Items 已分配
- [ ] 文档已归档
- [ ] 知识已沉淀
- [ ] 代码仓库已清理
- [ ] 监控告警已交接（如转入维护期）
- [ ] 运维手册已交接
- [ ] 项目记忆已更新

## 硬性规则

- ✅ **必须对照立项时的成功指标验收** — 不能忘记当初为什么做这个项目
- ✅ **复盘必须包含"待改进"** — 只说好的不叫复盘
- ✅ **Action Items 必须有负责人和截止日期** — 没有负责人的行动项等于没行动
- ✅ **文档必须归档到指定路径** — 散落各处的文档等于丢失
- ✅ **知识沉淀必须可复用** — 不能复用的经验只是日记
- ✅ **代码仓库必须清理临时分支** — 保持仓库整洁
- ❌ 禁止跳过复盘直接收尾 — 不复盘的项目无法改进
- ❌ 禁止文档散落在个人电脑 — 必须归档到项目仓库
- ❌ 禁止 Action Items 无跟踪 — 复盘的目的是改进，不是走形式

## 反模式

- ❌ "项目做完了，复盘以后再说" — 以后再说等于永远不说
- ❌ 复盘只说好的 — 自我感动不产生价值
- ❌ 文档写完就不管了 — 散落在各处的文档等于没有文档
- ❌ 经验只存在脑子里 — 人走了经验就没了
- ❌ Action Items 永远 Pending — 复盘不落地等于白复盘
- ❌ 不对照立项指标验收 — 偏离了初心还不自知
