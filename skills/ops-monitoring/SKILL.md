# Ops Monitoring


## 负责代理

`backend-developer` — 运维监控由后端开发工程师代理负责，确保日志、告警和巡检体系完善。

## 何时使用

- 项目部署上线后，需要建立运维监控体系时
- 需要配置日志收集、性能监控、告警机制时
- 需要制定定期巡检和数据备份策略时
- 系统出现线上问题，需要完善监控覆盖时
- 需要建立运维手册和应急响应流程时

**触发关键词**: "运维"、"监控"、"告警"、"巡检"、"备份"、"日志收集"、"Prometheus"、"Grafana"

## 与其他技能的关系

```
deploy (部署上线)
    ↓
ops-monitoring (运维监控) ← 部署后的长期运维阶段
    ↓
project-closure (项目收尾) ← 运维稳定后可进入收尾
```

> **衔接规则**: `deploy` 技能负责"把应用跑起来"，`ops-monitoring` 负责"让应用持续稳定运行"。两者衔接点为部署后的健康检查。

## 执行流程

### Phase 1: 日志监控方案

**目标**: 建立全链路日志收集与查询能力。

1. **日志规范**
   - 统一日志格式：JSON 结构化日志
   - 日志级别：DEBUG / INFO / WARNING / ERROR / CRITICAL
   - 必含字段：timestamp、level、request_id、module、message
   - 敏感信息脱敏规则（密码、Token、身份证号等）

2. **日志收集架构**

   | 方案 | 适用场景 | 成本 |
   |------|----------|------|
   | ELK（Elasticsearch + Logstash + Kibana） | 中大型项目，需要全文搜索 | 中高 |
   | Loki + Grafana | 轻量级，与 Prometheus 统一面板 | 低 |
   | 云服务商日志（CloudWatch / 阿里云 SLS） | 云原生项目，免运维 | 按量付费 |
   | 文件日志 + logrotate | 个人项目极简方案 | 免费 |

   > **[技术栈条件]** 日志方案选择由项目 `tech-stack.md` 和部署环境决定。

3. **日志查询场景**
   - 按 request_id 追踪完整请求链路
   - 按错误级别筛选（ERROR + CRITICAL）
   - 按时间范围 + 关键词搜索
   - 慢查询日志（响应时间 > 阈值）

### Phase 2: 性能监控方案

**目标**: 实时掌握系统运行状态，发现性能瓶颈。

1. **基础设施监控**
   - CPU 使用率
   - 内存使用率
   - 磁盘空间和 I/O
   - 网络流量

2. **应用层监控**
   - API 响应时间（P50 / P95 / P99）
   - 请求量（QPS / RPS）
   - 错误率（4xx / 5xx 占比）
   - 活跃连接数

3. **数据库监控**
   - 慢查询（> 100ms）
   - 连接池使用率
   - 索引命中率
   - 锁等待情况

4. **监控工具选型**

   | 工具 | 监控范围 | 特点 |
   |------|----------|------|
   | Prometheus + Grafana | 基础设施 + 应用 | 开源免费，社区活跃 |
   | 云服务商监控 | 基础设施 | 免配置，与云资源集成 |
   | APM（SkyWalking / Jaeger） | 链路追踪 | 微服务场景必备 |

   > **[技术栈条件]** 监控工具和指标采集方式由项目 `tech-stack.md` 定义。

5. **监控面板设计**
   - 概览面板：系统健康度一览（红/黄/绿）
   - API 面板：响应时间、错误率、QPS
   - 数据库面板：慢查询、连接数、锁等待
   - 基础设施面板：CPU、内存、磁盘、网络

### Phase 3: 告警机制

**目标**: 异常发生时第一时间通知，避免被动发现。

1. **告警分级**

   | 级别 | 触发条件 | 通知方式 | 响应时间 |
   |------|----------|----------|----------|
   | **P0 - 紧急** | 服务不可用、数据丢失 | 电话 + 短信 + 即时通讯 | 立即 |
   | **P1 - 严重** | 核心功能异常、错误率飙升 | 短信 + 即时通讯 | 15 分钟内 |
   | **P2 - 警告** | 性能下降、资源紧张 | 即时通讯（飞书/钉钉） | 1 小时内 |
   | **P3 - 提示** | 容量预警、非核心异常 | 邮件 / 即时通讯 | 工作日处理 |

2. **告警规则示例**

   ```
   # P0 告警
   - 服务健康检查连续 3 次失败
   - 数据库连接失败
   - 磁盘空间 < 5%

   # P1 告警
   - API 5xx 错误率 > 5%
   - API P99 响应时间 > 2s
   - 内存使用率 > 90%

   # P2 告警
   - CPU 使用率 > 80%（持续 5 分钟）
   - 慢查询数 > 10/min
   - 日志 ERROR 数量 > 50/min
   ```

3. **告警通知渠道**
   - 即时通讯：飞书机器人 / 钉钉机器人 / 企业微信
   - 短信：阿里云短信 / 腾讯云短信
   - 邮件：SMTP / 邮件服务 API
   - 电话：云服务商电话告警

4. **告警治理**
   - 避免告警风暴：同类告警合并、静默窗口
   - 告警去噪：自动恢复的告警降级
   - 定期评审：每月 review 告警有效性，清理无效告警

### Phase 4: 定期巡检

**目标**: 主动发现潜在问题，防患于未然。

**巡检清单**：

| 频率 | 巡检项 | 检查内容 |
|------|--------|----------|
| **每日** | 服务健康 | 健康检查端点正常 |
| **每日** | 日志异常 | 前 24h ERROR/CRITICAL 日志 |
| **每日** | 备份状态 | 数据库备份是否成功 |
| **每周** | 磁盘空间 | 磁盘使用率 < 80% |
| **每周** | 依赖更新 | 安全漏洞扫描 |
| **每周** | 证书有效期 | SSL 证书 > 30 天过期 |
| **每月** | 性能趋势 | 月度性能报告对比 |
| **每月** | 容量评估 | 资源使用趋势预测 |

### Phase 5: 数据备份策略

**目标**: 确保数据可恢复，应对灾难场景。

1. **备份策略**

   | 数据类型 | 备份频率 | 保留周期 | 备份方式 |
   |----------|----------|----------|----------|
   | 数据库全量 | 每日 | 30 天 | pg_dump / mysqldump |
   | 数据库增量 | 每小时 | 7 天 | WAL 归档 / binlog |
   | 用户上传文件 | 每日 | 30 天 | rsync / 对象存储版本 |
   | 配置文件 | 每次变更 | 永久 | Git 版本控制 |
   | 日志文件 | 每日 | 14 天 | 压缩归档 |

2. **备份验证**
   - 每月执行一次恢复演练
   - 验证备份文件完整性（校验和）
   - 记录恢复演练结果

3. **灾备方案**
   - 同城双活（如预算允许）
   - 异地冷备（至少每日同步）
   - RTO（恢复时间目标）：< 4 小时
   - RPO（恢复点目标）：< 1 小时

## 硬性规则

- ✅ **必须有监控** — 没有监控的系统等于盲飞
- ✅ **必须有告警** — 不能靠用户投诉发现问题
- ✅ **必须有备份** — 数据丢失是不可逆的灾难
- ✅ **告警必须分级** — 所有告警都一样紧急等于没有告警
- ✅ **备份必须验证** — 未验证的备份等于没有备份
- ✅ **必须有运维手册** — 不能只存在某个人的脑子里
- ✅ **日志必须结构化** — JSON 格式便于查询和分析
- ✅ **敏感信息必须脱敏** — 日志中禁止出现密码、Token
- ❌ 禁止告警风暴 — 同类告警需合并
- ❌ 禁止无告警直接上线 — 至少配置 P0/P1 告警
- ❌ 禁止生产环境直接调试 — 使用日志和监控排查

## 反模式

- ❌ "上线后再加监控" — 没有监控的上线等于裸奔
- ❌ 所有告警都发短信 — 告警疲劳后真正紧急的被忽略
- ❌ 只备份不验证 — 恢复时才发现备份损坏
- ❌ 日志全写 INFO — 关键信息淹没在海量日志中
- ❌ 没有运维手册 — 一个人离职系统就没人会运维
- ❌ 告警规则从不 review — 系统变了告警规则还停在原点
