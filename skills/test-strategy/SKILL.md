# Test Strategy

## 负责代理

`test-engineer` — 测试策略制定和系统级测试由测试工程师代理负责，覆盖测试分层、用例设计、Bug 管理和测试报告。

## 何时使用

- 单元测试（TDD）完成后，需要进行系统级测试时
- 需要制定测试计划、测试范围和排期时
- 需要进行集成测试、性能测试、安全测试、回归测试时
- 需要建立 Bug 管理流程时
- 版本发布前，需要系统化测试验收时

**触发关键词**: "测试计划"、"集成测试"、"性能测试"、"安全测试"、"回归测试"、"Bug管理"、"测试报告"

## 与其他技能的关系

```
brainstorming → system-design → test-strategy（设计阶段）
                                      ↓
                               executing-plans → test-strategy（执行阶段）
                                      ↓
                               verification（完成前验证）
```

> **衔接规则**: `test-strategy` 分为两个阶段：
> - **设计阶段**：在编码前输出 `test-design.md`，定义测试分层、自动化策略和覆盖目标
> - **执行阶段**：在编码完成后按设计文档执行测试

## 执行流程

### Phase 0: 设计阶段（输出 test-design.md）

**目标**: 在编码前完成测试方案设计，确保测试覆盖率和自动化策略。

#### Step 1: 测试分层定义

根据项目技术栈定义测试金字塔：

| 测试层 | 范围 | 工具 | 覆盖率目标 | 运行频率 |
|--------|------|------|-----------|----------|
| 单元测试 | 函数/类/方法 | Pytest / Jest | >= 80% | 每次提交 |
| 集成测试 | 模块间交互 | Pytest + TestClient | >= 60% | 每次 PR |
| API 测试 | 接口契约 | Pytest + httpx | 100% 接口 | 每次部署 |
| E2E 测试 | 核心用户流程 | Playwright / Cypress | >= 5 条核心路径 | 每次发布 |
| 性能测试 | 响应时间/并发 | Locust / k6 | 基线达标 | 每次大版本 |
| 安全测试 | OWASP Top 10 | 手动 + 工具 | 关键项全覆盖 | 每次发布 |

#### Step 2: 自动化测试策略

定义 CI/CD 中的测试流水线：

```
Git Push -> Lint -> 单元测试 -> 构建 -> 集成测试 -> API测试 -> E2E测试 -> 部署
```

**测试数据管理**:
- 使用 Fixtures / Factories 生成测试数据
- 每个测试用例独立，不依赖执行顺序
- 集成测试使用独立数据库（Docker）
- Mock 外部服务（支付、邮件、SMS）

#### Step 3: 测试用例清单

列出核心功能的测试用例（按模块）：

| 模块 | 测试用例 | 类型 | 优先级 |
|------|----------|------|--------|
| 认证 | 登录成功 | 集成 | P0 |
| 认证 | 密码错误 | 集成 | P0 |
| 认证 | Token过期 | 单元 | P0 |
| 用户 | 获取个人信息 | 集成 | P0 |
| ... | ... | ... | ... |

#### Step 4: 覆盖率目标与门禁

| 类型 | 目标 | 门禁（不达标则阻止合并） |
|------|------|--------------------------|
| 行覆盖率 | >= 80% | >= 70% |
| 分支覆盖率 | >= 70% | >= 60% |
| 核心模块 | >= 90% | >= 85% |

### Phase 2: 测试用例编写

**目标**: 为每个测试维度编写具体用例。

1. **集成测试用例**
   - 覆盖模块间交互（API → Service → Repository → DB）
   - 覆盖跨模块数据流（如：用户注册 → 发送邮件 → 记录日志）
   - 覆盖第三方服务集成（Mock + 真实调用）

2. **性能/压力测试方案**
   - 定义性能指标基线：
     - API 响应时间 P99 < ?ms
     - 并发用户数支持 ? 
     - 吞吐量 ? req/s
   - 设计压测场景：逐步加压 / 持续高压 / 峰值冲击
   - 工具选择：locust / k6 / Apache Bench

   > **[技术栈条件]** 性能测试工具和指标基线由项目 `tech-stack.md` 定义。

3. **安全测试检查清单**
   - 输入校验：SQL 注入、XSS、CSRF
   - 认证授权：越权访问、Token 过期、权限提升
   - 敏感数据：日志泄露、响应体泄露、传输加密
   - 依赖安全：已知漏洞扫描（pip-audit / npm audit）

4. **兼容性测试**
   - 浏览器兼容性（如适用）
   - API 版本兼容性
   - 数据库迁移兼容性

5. **回归测试策略**
   - 全量回归：每次大版本发布
   - 选择性回归：基于变更影响范围选择用例
   - 自动化回归：将核心路径测试自动化

### Phase 3: 测试执行

1. **按计划执行各类型测试**
2. **记录测试结果**
3. **发现 Bug 时进入 Bug 管理流程**

### Phase 4: Bug 管理

**Bug 生命周期**:

```
发现 → 提交 → 分配 → 修复 → 验证 → 关闭
                                    ↓
                                重新打开（验证失败）
```

**Bug 分级标准**:

| 级别 | 定义 | 响应时间 | 示例 |
|------|------|----------|------|
| **P0 - 阻塞** | 核心功能不可用，无规避方案 | 立即修复 | 登录失败、数据丢失、支付报错 |
| **P1 - 严重** | 核心功能受损，有规避方案 | 24h 内修复 | 搜索结果错误、特定浏览器崩溃 |
| **P2 - 一般** | 非核心功能异常 | 本迭代修复 | 样式错位、文案错误 |
| **P3 - 轻微** | 体验问题，不影响功能 | 下迭代修复 | 动画卡顿、对齐不齐 |

## 硬性规则

- ✅ **测试计划必须在开发前制定** — 不是写完代码才想怎么测
- ✅ **性能测试必须定义量化基线** — "性能还行"不是结论
- ✅ **安全测试必须覆盖 OWASP Top 10** — 至少检查注入、XSS、CSRF
- ✅ **Bug 必须分级管理** — P0/P1 必须在发布前修复
- ✅ **测试报告必须包含量化数据** — 通过率、响应时间、并发数
- ✅ **回归测试必须自动化核心路径** — 手动回归不可持续
- ❌ 禁止跳过安全测试直接上线
- ❌ 禁止 P0/P1 Bug 未修复就发布
- ❌ 禁止测试报告只写"测试通过"无数据支撑

## 反模式

- ❌ "开发完了随便测测" — 没有计划的测试等于没测
- ❌ 只测 Happy Path — 边界条件和异常场景才是 Bug 温床
- ❌ 性能测试只看平均值 — P99 才是用户体验的真实反映
- ❌ Bug 记录只有标题没有复现步骤 — 开发者无法复现就无法修复
- ❌ 安全测试只靠工具扫描 — 工具漏报率高，需人工验证
