# Performance Tuning


## 负责代理

`architect` — 性能优化由架构师代理负责，确保优化方案有量化基线和回滚策略。

## 何时使用

- API 响应时间过长时
- 数据库查询慢时
- 前端页面加载慢时
- 系统内存使用过高时
- 用户反馈性能问题时

**触发关键词**: "优化性能"、"查询慢"、"响应慢"、"卡顿"、"性能问题"

## 与其他技能的关系

```
brainstorming → system-design → performance-tuning（设计阶段）
                                          ↓
                                   executing-plans（实现阶段）
```

> **衔接规则**: `performance-tuning` 分为两个阶段：
> - **设计阶段**：在编码前输出 `performance-design.md`，定义性能指标基线和缓存策略
> - **实现阶段**：在编码后按设计文档执行优化

## 执行流程

### Phase 0: 设计阶段（输出 performance-design.md）

**目标**: 在编码前完成性能与缓存方案设计，避免上线后亡羊补牢。

#### Step 1: 性能指标基线定义

根据项目需求定义可达成的性能目标：

| 指标 | 定义 | 目标值 | 测量方法 |
|------|------|--------|----------|
| API 响应时间 P50 | 50% 请求的响应时间 | < 200ms | APM / 日志 |
| API 响应时间 P95 | 95% 请求的响应时间 | < 500ms | APM / 日志 |
| API 响应时间 P99 | 99% 请求的响应时间 | < 1s | APM / 日志 |
| 页面首屏加载 | FCP / LCP | < 2.5s | Lighthouse |
| 并发用户数 | 同时在线用户 | 按预期 | 压测工具 |
| 吞吐量 | 每秒请求数 | 按预期 | 压测工具 |

#### Step 2: 缓存分层策略设计

定义各层缓存的策略和参数：

| 缓存层 | 技术选择 | 适用数据类型 | TTL | 失效策略 |
|--------|----------|-------------|-----|----------|
| 浏览器缓存 | Cache-Control / ETag | 静态资源 | 1年 | 文件名哈希 |
| CDN 缓存 | Cloudflare（开源协议）/ 自托管 CDN | 静态资源、API响应 | 可配置 | Purge API |
| 应用缓存 | Redis / 内存 | 高频查询结果 | 1-5分钟 | 主动失效 |
| 数据库缓存 | PostgreSQL Buffer | 热数据 | 自动 | LRU |
| ORM 缓存 | SQLAlchemy Cache | 查询结果 | 按需 | 写入穿透 |

**缓存穿透/击穿/雪崩防护**:

| 问题 | 描述 | 防护策略 |
|------|------|----------|
| 缓存穿透 | 查询不存在的数据 | 布隆过滤器 / 空值缓存 |
| 缓存击穿 | 热点Key过期 | 互斥锁 / 永不过期+异步刷新 |
| 缓存雪崩 | 大量Key同时过期 | TTL随机化 / 多级缓存 |

#### Step 3: 数据库查询优化设计

定义需要优化的查询和索引策略：

| 优化项 | 策略 | 说明 |
|--------|------|------|
| N+1 查询 | `selectinload` / `joinedload` | 预加载关联数据 |
| 深分页 | Cursor分页替代Offset | 大数据量场景 |
| 复杂查询 | 索引覆盖 / 物化视图 | 报表类查询 |
| 慢查询 | EXPLAIN ANALYZE | 上线前验证 |

#### Step 4: 前端性能优化设计

| 优化项 | 策略 | 说明 |
|--------|------|------|
| 代码分割 | `React.lazy()` + `Suspense` | 按路由拆分 |
| 图片优化 | WebP + 懒加载 + 响应式尺寸 | 减少传输量 |
| 字体优化 | `font-display: swap` + 子集化 | 避免FOIT |
| 预加载 | `<link rel="preload">` | 关键资源优先 |

### Phase 1: 测量与分析

**目标**: 量化性能问题，定位瓶颈。

#### 后端性能分析

1. **测量响应时间**:
   - 使用 `timeit` 测量函数执行时间
   - 使用 `structlog` 记录请求耗时
   - 使用 APM 工具（如 Pyroscope、OpenTelemetry）追踪性能

2. **数据库查询分析**:
   - 使用 `EXPLAIN ANALYZE` 分析慢查询
   - 检查查询是否命中索引
   - 识别 N+1 查询问题

3. **内存分析**:
   - 使用 `memory_profiler` 分析内存使用
   - 检查是否有内存泄漏

#### 前端性能分析

1. **页面加载分析**:
   - 使用 Lighthouse 测量 Core Web Vitals
   - 分析 Network 面板的资源加载顺序
   - 识别阻塞渲染的资源

2. **运行时性能**:
   - 使用 Performance 面板分析 JS 执行时间
   - 使用 React DevTools Profiler 分析组件渲染
   - 检查不必要的 re-render

### Phase 2: 制定优化计划

**目标**: 根据分析结果，制定优先级明确的优化计划。

优化优先级:
1. **高影响低成本**: 索引优化、查询优化、代码优化
2. **高影响高成本**: 架构调整、缓存策略、异步处理
3. **低影响低成本**: 代码清理、小优化
4. **低影响高成本**: 新技术引入、大规模重构

### Phase 3: 实施优化

**目标**: 逐步实施优化措施。

#### 数据库优化

1. **添加索引**:
   - 为高频查询的 WHERE 条件添加索引
   - 为 JOIN 条件添加索引
   - 使用复合索引优化多条件查询

2. **优化查询**:
   - 使用 `selectinload` / `joinedload` 解决 N+1 问题
   - 使用 `subqueryload` 优化复杂查询
   - 避免 `SELECT *`，只查询需要的字段

3. **批量操作**:
   - 使用 `bulk_insert_mappings` / `bulk_update_mappings`
   - 避免循环中执行数据库查询

#### API 优化

1. **添加缓存**:
   - 使用 Redis 缓存高频查询结果
   - 设置合理的 TTL
   - 实现 Cache-Aside 模式

2. **分页优化**:
   - 使用 Cursor 分页替代 Offset 分页（大数据量）
   - 限制每页返回的数据量

3. **异步处理**:
   - 使用 Background Tasks 处理耗时操作
   - 使用 Celery 处理异步任务

#### 前端优化

1. **代码分割**:
   - 使用 `React.lazy()` + `Suspense` 实现懒加载
   - 按需加载非关键代码

2. **状态管理优化**:
   - 使用 `React.memo()` 避免不必要的重渲染
   - 使用 `useMemo()` / `useCallback()` 缓存计算结果

3. **资源优化**:
   - 使用 WebP/AVIF 格式图片
   - 图片懒加载
   - 启用 Gzip/Brotli 压缩

### Phase 4: 验证

**目标**: 确认优化效果。

1. **重新测量**: 使用相同的测量工具验证性能改善
2. **对比基准**: 对比优化前后的性能指标
3. **运行测试**: 确保优化未引入回归问题
4. **监控观察**: 部署后持续监控性能指标

## 硬性规则

- ✅ **优化前必须测量** — 无数据不优化
- ✅ **优化后必须验证** — 确保优化有效
- ✅ **优化必须有回滚方案** — 准备好回退步骤
- ✅ **数据库优化前必须备份** — 防止数据丢失
- ✅ **代码优化必须保持功能不变** — 不改变外部行为
- ❌ **禁止凭感觉优化** — 必须基于测量数据
- ❌ **禁止优化后不验证** — 无法确认是否有效
- ❌ **禁止在无备份的情况下优化数据库** — 风险极高
- ❌ **禁止优化时引入新功能** — 专注于性能改善

## 反模式

- ❌ "优化所有可能的地方" — 过度优化，浪费时间
- ❌ 优化前不测量 — 不知道优化是否有效
- ❌ 优化后不验证 — 可能引入回归问题
- ❌ 只为优化而优化 — 优化应基于实际问题
- ❌ 使用复杂技术解决简单问题 — 过度设计
