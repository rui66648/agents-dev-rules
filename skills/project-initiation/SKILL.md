# Project Initiation


## 负责代理

`architect` — 项目启动由架构师代理负责，确保需求收集、可行性分析和立项文档完整。

## 何时使用

- 从零开始一个新项目时
- 需要明确项目目标、范围、预算和团队时
- 需要进行技术/经济/时间可行性评估时
- 个人项目需要轻量化立项，确认技术选型和范围边界时

**触发关键词**: "新项目"、"项目启动"、"立项"、"可行性分析"、"项目规划"

## 执行流程

### Phase 1: 需求收集

**目标**: 理解核心诉求，明确"为谁解决什么问题"。

1. **利益相关方识别**
   - 个人项目：明确最终用户画像（哪怕是"自己"）
   - 团队项目：列出客户、业务方、开发方、运维方

2. **核心诉求收集**
   - 采用结构化访谈或自问自答方式：
     - 要解决什么问题？（问题陈述）
     - 谁会遇到这个问题？（目标用户）
     - 现有方案有什么不足？（竞品/现状分析）
     - 成功长什么样？（成功指标）

3. **输出**: 需求收集清单（结构化笔记）

### Phase 2: 可行性分析

**目标**: 评估项目是否值得做、能否做。

| 维度 | 评估内容 | 个人项目轻量化 |
|------|----------|---------------|
| **技术可行性** | 技术栈是否熟悉？是否有成熟方案？关键技术风险？ | 简化为"技术选型确认" |
| **经济可行性** | 开发成本、服务器成本、第三方服务费用 | 简化为"成本估算（月度）" |
| **时间可行性** | 预估工期、关键里程碑、是否有硬性截止日期 | 简化为"时间预估（周）" |
| **运维可行性** | 上线后维护成本、监控方案、是否有能力独立运维 | 简化为"运维方案确认" |

> **[技术栈条件]** 技术选型评估由项目 `tech-stack.md` 决定。若无 `tech-stack.md`，本阶段需同时完成技术选型并创建该文件。

### Phase 3: 项目立项

**目标**: 形成正式的项目启动文档。

输出文档结构（`docs/project-initiation.md`）：

```markdown
# 项目立项书: [项目名称]

## 1. 项目概述
- 项目名称:
- 一句话描述:
- 目标用户:

## 2. 问题陈述
- 核心问题:
- 现有方案不足:
- 预期价值:

## 3. 成功指标
- 可量化的成功标准（如：DAU > 100、API 响应 < 200ms）
- 验收方式

## 4. 范围边界
### In Scope（本次包含）
### Out of Scope（明确排除）

## 5. 可行性评估
### 技术可行性
### 经济可行性
### 时间可行性
### 运维可行性

## 6. 技术选型
（引用或创建 tech-stack.md）

## 7. 里程碑规划
| 里程碑 | 预计完成时间 | 交付物 |
|--------|-------------|--------|

## 8. 风险登记
| 风险 | 概率 | 影响 | 应对策略 |
|------|------|------|----------|
```

### Phase 4: 进入开发流程

立项文档完成后，进入标准开发流程：

```
project-initiation → brainstorming（具体功能需求探索）→ writing-plans → ...
```

> **衔接规则**: 立项文档是 `brainstorming` 的前置输入。`brainstorming` 技能在 Phase 1 上下文探索时，应读取 `docs/project-initiation.md` 获取项目全局上下文。

## 个人项目轻量化模式

个人项目可跳过完整立项流程，仅保留三个核心步骤：

1. **项目目标定义** — 一段话说明"做什么、为谁做、为什么做"
2. **技术选型确认** — 确认或创建 `tech-stack.md`
3. **范围边界** — 明确 In Scope / Out of Scope

输出可简化为 `docs/project-initiation.md` 中的前 4 个章节。

## 时间分配原则（v1.1.0，ADR-006）

> 原"人机时间分配表 / 一天开发节奏表"面向"人逐步指挥聊天机器人"的范式，已删除。核心只剩一条：**把人的时间花在高风险决策上**——需求、架构、安全、数据等难以回滚的决策需要人参与；编码与验证尽可能交给 Agent，并以可执行验证兜底。

## 最小必要文件集（MVP 阶段）

> 个人小项目不必生成全部文档，以下为最小必要集：

```
project/
├── README.md                  ← 必须有：项目介绍
├── .env.example               ← 必须有：环境变量模板
├── .gitignore                 ← 必须有：忽略规则
├── AGENTS.md                  ← 必须有：构建规则
├── tech-stack.md              ← 必须有：技术栈定义
├── CHANGELOG.md               ← 建议有：版本记录
├── docs/
│   ├── PRD.md                 ← 想清楚做什么
│   ├── database-schema.md     ← 表结构（如有数据库）
│   └── deploy-guide.md        ← 怎么部署
└── tests/                     ← 核心逻辑测试
```

> **原则**: 文件是给自己未来看的，够用就行，别为了写文档而写文档。AI 可以一键生成，但只生成你真正会回头看的。

## MVP 快速启动验证清单

> 个人项目从 0 到 1 时，在立项后、进入详细需求探索前，使用此清单快速验证"是否可以直接开始编码"。

### 清单（5 分钟自检）

| 检查项 | 通过标准 | 你的答案 |
|--------|----------|----------|
| **核心问题已明确** | 能用一句话描述"为谁解决什么问题" | [ ] 是 / [ ] 否 |
| **技术选型已确认** | 已创建或确认 `tech-stack.md` | [ ] 是 / [ ] 否 |
| **最小功能集已划定** | 列出 ≤5 个 MVP 功能，标注优先级 | [ ] 是 / [ ] 否 |
| **边界已清晰** | 明确 In Scope / Out of Scope | [ ] 是 / [ ] 否 |
| **成功标准可量化** | 至少有一个可验证的成功指标 | [ ] 是 / [ ] 否 |
| **部署目标已确定** | 知道最终部署到哪里（Docker Compose / VPS / ...） | [ ] 是 / [ ] 否 |

### 通过标准

- **6 项全通过**：可以直接进入 `brainstorming` 或 `writing-plans`，无需完整立项流程
- **4-5 项通过**：补充缺失项后进入开发流程
- **≤3 项通过**：执行完整立项流程（Phase 1-3），不要急于编码

> **核心原则**：MVP 验证清单的目的是**防止过度准备**，而不是鼓励跳过思考。6 项全通过 = "想得够清楚了，可以开始动手"。

## 硬性规则

- ✅ **必须明确范围边界** — In Scope / Out of Scope 缺一不可，防止 Scope Creep
- ✅ **必须评估技术可行性** — 不熟悉的技术栈需标注为风险
- ✅ **必须定义可量化的成功指标** — "做得好用"不算指标
- ✅ **必须创建或确认 `tech-stack.md`** — 后续所有技能依赖此文件
- ✅ **立项文档必须保存到 `docs/project-initiation.md`** — 供后续技能读取
- ❌ 禁止跳过可行性分析直接开发
- ❌ 禁止立项文档与实际开发脱节（立项后不再参考）
- ❌ 禁止使用模糊的成功指标（如"用户满意"、"性能好"）

## 反模式

- ❌ "先写代码再说" — 没有目标的项目容易迷失方向
- ❌ "什么都要做" — 不设 Out of Scope 导致范围蔓延
- ❌ 立项文档写完就归档 — 应作为活文档持续更新
- ❌ 技术选型拍脑袋 — 至少需要 2 个候选方案对比
- ❌ 成功指标不可量化 — 无法判断项目是否成功
